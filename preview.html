01 · Before

Every client got their own style guide.

A new client meant a new style guide: typography, colour palette, icons and micro components. Then came the work of recreating the happy flow and attaching each screen to the new styles.

Underneath, it was the same document every time. Same sections and same type tiers. Only the values changed. Because the values were typed onto the canvas as notes, not bound to anything, one change meant touching every screen again.

The shape of the problem

  • A style guide rebuilt per client
  • Screens re-attached to new styles by hand
  • Design: a few days per client
  • Engineering: a few more days on top

Clients, each with their own file page

Simplified recreations. The real guides share the same structure, with the same type tiers and component sets redrawn for each client.

02 · One onboarding, up close

ING: promised in a week, took about two.

ING came on before the design system was ready. Engineering and QA needed reference screens, so I created a style guide, the components and every screen they needed to build against: the landing page, hotel listing with filters and map, hotel details with gallery and surroundings, room listing, and booking confirmation.

That was roughly 90 screens across mobile and desktop. Design took me about two days. Because there was no system to inherit from, engineering built it all again, and the full onboarding took about two weeks.

06 · How it was made

Built from a rectangle, before AI.

I made every part of this by hand, in Figma. The button began as a rectangle: round the corners, bind the fill to a token, add a label, then define its states. No generators, no shortcuts.

The result covers about 35 components across Actions, Inputs, Navigation, Content, Feedback and Utility, plus foundations for colour, typography, border, spacing, elevation, grids, icons and shapes.

It's also honest work-in-progress. The file still has a parking lot, a modal marked [OLD] next to the new one, and a layout layer I'm still building. I'm cleaning it up as I go.

07 · Adding a new client

Roughly an hour of design.

  1. Research the paletteBrand guidelines make this faster. Without them, I read it from the client's product.
  2. Add a modeFill the brand's primitive scales in the Primitives collection.
  3. Map the semanticsPoint action, surface and text tokens at the new scales.
  4. Switch and testFlip the mode on real screens and check contrast and states.

Before

  • New style guide per client
  • Screens rebuilt and re-attached
  • ING: ~2 days design, ~2 weeks total

With the system

  • One new mode
  • Screens update on their own
  • ~1 hour design. The promise to clients: live in a day.

In practice, the full onboarding including engineering runs a little over a day.

08 · The product moved on

From Silk to Spice.

Silk, the original codebase

My first version was built for Silk, a hand-written codebase. As I understand it from engineering, the design system also lives in code there. If I change a value such as surface colour for one client, the change carries across all the others.

Spice, the new codebase

The product is moving to Spice, written entirely with AI. The design system has to carry across the move. The token structure is what makes that possible, because the code depends on what a token means, not how a screen was drawn.

09 · The rules

How designers and developers use it.

✓ Do

  • Use semantic tokens such as action/primary.
  • Let the brand mode change the look.
  • Describe what an element is, not what it looks like.

✕ Don't

  • Use a hardcoded hex code.
  • Reach for primitives when a semantic token exists.
  • Rebuild a component for one client.
